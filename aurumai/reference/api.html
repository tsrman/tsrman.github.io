API reference

AurumAI has two HTTP planes served by the same backend code with different audiences:

Plane Port Audience Used by
Business API 8000 Chat app users business-ui, runners, workers
Admin API 8001 Administrators admin-ui

Both authenticate with Keycloak access tokens (Authorization: Bearer ...). Each plane accepts only its own audience, so a chat token does not open the Admin API. Responses are mostly wrapped as {"data": ..., "meta": ...} (lists add pagination), and errors carry a bounded code.

Request and response schemas are not repeated here. With APP_DEBUG=true each plane serves interactive OpenAPI documentation at /docs and /redoc; it is disabled otherwise, so for a production deployment read the routers in business-backend/src/routers/ or run a development instance.

Paths below are relative to the plane's host. The business routes are mounted under /v1.

Conventions

  • Rate limits: per user, 300 ordinary requests and 30 chat streams per minute by default; over the limit the API answers 429.
  • Quota: model calls count against the organization's monthly request and token limits; when spent they are refused.
  • Capabilities gate actions; grants gate resources. A missing capability answers 403; a resource you cannot see answers 404.
  • Service-only routes (everything under /v1/internal/* and /v1/hermes/chat/completions, the Hermes MCP bridge and the preview checks) are for the platform's own services. They accept service credentials or session tokens, not browser tokens, and are not a client API.
  • Health: GET /health (liveness), GET /ready (dependencies), GET /metrics.

The Admin API also serves the agent-definition and knowledge-base routes above, so the admin app can manage them.

Authentication

Sign in uses OpenID Connect through Keycloak (realm aurum-ai). Browser clients are business-ui and admin-ui; each issues tokens with its own audience. The runner, tool workers and Hermes sandboxes use session tokens minted by the backend that carry identity only, have their own audience, and are valid only while their session or turn is open. Authorization is evaluated live on every request.

For local scripts, a development token can be fetched with the password grant against the Keycloak token endpoint using the user or admin fixture accounts. Do not do that outside development.
